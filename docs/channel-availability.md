# Channel availability

The channel availability page exposes the latest health of explicitly configured channels to authenticated users. Administration endpoints require the admin role. Monitoring is globally disabled by default through `ChannelMonitorEnabled` and should only be enabled after monitors have been reviewed.

## Probe policy

- Text models use the existing channel test path on the configured interval. Results are stored without channel credentials, and public responses omit raw upstream errors.
- Image and video models are never actively generated by this monitor. Their current state is derived from terminal real tasks for the same channel and model.
- The `cy-sd1-omni-*` and `cy-sd4-minimax-*` video families are explicitly treated as passive media even though their public model names do not contain `video` or `veo`.
- Passive matching checks `client_model_name`, `origin_model_name`, and `upstream_model_name`. Queries select terminal metadata only and do not read task payloads or private task data.
- Content or request validation failures, platform storage/worker failures, configuration errors, and unclassified failures do not overwrite the latest effective channel state.

## Passive state rules

Image observations use a 30-minute freshness window. The latest five effective observations are evaluated: a latest success with at least four successes is operational, no successes or three consecutive channel failures is unavailable, and other outcomes are degraded.

Video observations use a 24-hour freshness window because traffic is lower. The latest effective success is immediately operational, one or two latest channel failures are degraded, and three consecutive channel failures are unavailable.

When no effective observation exists inside the freshness window, the state is unknown. Availability percentages use the latest 20 effective image observations or latest five effective video observations within that same window.

## Initial monitor configuration

- Create one text monitor per published group and select one fixed text model available in that group. Enable image and video aggregation once per category; do not create media monitors per channel.
- Text monitoring is configured by group and one fixed text model. Each round tries enabled channels in that group that support the model, stopping immediately after the first operational result; only an all-failed round is unavailable. Channel-level failures remain administrator diagnostics and are never exposed publicly.
- Image and video monitoring is enabled per category rather than per channel. The public list reads currently listed media models across every enabled channel, evaluates real tasks passively, converts internal names through `ToPublicModelName`, and merges duplicate public names. Delisted exact models disappear on the next aggregation and media monitoring never sends generation requests.
- Public media aggregation loads recent terminal task metadata for all monitored channels in one batch and evaluates configured models in memory, avoiding one task-table scan per model.
- Keep global monitoring disabled while monitors are created and reviewed. Enable it only after the configured channel IDs, model names, visibility, and probe kinds have been verified.

## Public response contract

The authenticated user endpoint returns only the public display name, category (`text`, `image`, or `video`), latest state, availability, average latency, and 48 anonymous status bars. Text and media intentionally use different timeline cadences: each text bar is one completed group probe round (normally every 300 seconds), while each image or video bar is one half-hour bucket covering the latest 24 hours. Text timelines retain the latest 48 probe rounds without half-hour folding; before 48 rounds exist, anonymous unknown placeholders fill the leading slots and are not counted as observations. A text round is operational as soon as any eligible channel succeeds. A media bucket aggregates all effective tasks from that interval: at least 80% success is operational, no success or three latest consecutive channel failures is unavailable, and other mixed outcomes are degraded. Empty media buckets carry the previous trustworthy state (looked up from the preceding 24 hours) with `carried=true`; carried buckets keep the media timeline continuous but do not count toward availability. Anonymous points expose neither timestamps nor per-observation latency. The master node builds complete 7/15/30-day public snapshots on startup and every 30 minutes, while replacing only their text sections every five minutes so text bars advance independently without re-aggregating media. Requests only read Redis or in-memory snapshots and never synchronously aggregate database history. Snapshots live for two hours so a failed refresh continues serving the previous result. Media task snapshots retain a shared scan cursor, so refreshes query only newly completed tasks and merge them into the rolling 48-hour source window; only a cold background aggregation performs a full-window query. It does not expose monitor or channel identifiers, channel/provider names, internal model names, raw errors, sample counts, or last update time. Disabled channels are excluded even if a stale monitor configuration remains. The administrator endpoints retain the diagnostic view.

Text items are keyed dynamically by groups on enabled channels that provide at least one listed text model. A probe round tries eligible channels in sequence and only advances after a failure; the first operational result ends the round, reducing probe cost. Image and video items are keyed by category plus public model name; internal, client-facing, and upstream model aliases are treated as the same task identity. When several enabled channels provide the same public media model, their real tasks are merged without exposing channel identity.

## Release verification

1. Keep global monitoring disabled immediately after deployment and confirm migrations created `channel_monitors` and `channel_monitor_results`.
2. As an admin, create one text monitor and one media monitor. Confirm the media monitor reports `media_passive` and that running it does not create a generation task.
3. Enable monitoring, then verify `/api/channel-monitors` exposes only enabled and visible public entries without monitor IDs, sample counts, internal model names, `channel_id`, channel names, credentials, raw errors, task payloads, or private task data.
4. Confirm a recent media success is reflected as operational and three consecutive channel failures are reflected as unavailable.
5. Verify the `/channel-availability` page on desktop and mobile, including the text/image/video tabs, public model names, admin configuration, and regular-user status views.
