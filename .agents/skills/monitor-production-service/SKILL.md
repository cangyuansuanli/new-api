# 监控生产服务

监控“用户能否完成目标”和“系统能否恢复”，不只监控进程是否存活。阈值、接口、域名、服务名和告警平台从仓库与线上发现。

## 建立监控地图

读取架构、Compose、健康端点、指标代码、部署脚本、备份流程和业务账目规则。按层列出：

- 外部入口：DNS、TLS、HTTP、SSE/WebSocket、长连接和关键静态资源；
- 应用：请求量、成功率、错误分类、延迟、并发和版本；
- 依赖：数据库连接/锁/复制延迟、Redis、队列年龄和对象存储；
- Worker：心跳、吞吐、任务状态、重试、超时和积压；
- 账号池：活跃数、隔离数、额度、认证失败和限流；
- 恢复能力：备份新鲜度、异地上传、恢复演练时间和证书续期；
- 业务不变量：账目平衡、异常消费、支付回调、退款、风险欠款或配额守恒。

为每项写明数据源、负责人、严重度、告警条件、持续时间、恢复条件和对应 runbook。

## 设计探测

- **Liveness** 只判断进程需不需要重启，不依赖所有外部服务。
- **Readiness** 判断实例能否接流量，覆盖必要依赖和角色状态。
- **外部合成探测** 从真实入口验证 DNS、TLS、代理和应用链路。
- **业务巡检** 使用只读或无副作用 API；有成本的真实任务必须限频、限额并获授权。
- **版本与拓扑探测** 检测活跃槽、镜像、Worker 节点和配置漂移。

不要让健康检查触发写入、扣费、全表扫描或上游高成本调用。

## 设置告警

以服务目标和历史基线设置阈值，不复制固定数字。优先告警：

- 多窗口错误率或延迟超标；
- 队列最老任务年龄持续增长；
- 活跃账号或健康 Worker 降至容量下限；
- 备份超龄、对象为空或异地上传失败；
- 磁盘、连接池、文件描述符接近耗尽；
- 账目不平、消费突增、支付回调异常；
- 证书接近过期或续期失败。

仅在状态变化时发送一次故障与一次恢复通知，或设置合理抑制/聚合。告警正文包含环境、症状、开始时间、关键指标、runbook 和请求/任务标识，不包含密钥或请求正文。

## 部署巡检

优先复用 Prometheus/OpenTelemetry、现有 agent 或项目监控脚本。定时脚本使用 systemd timer 或现有调度器，明确运行用户、工作目录、环境文件、超时和互斥；检查 `systemctl list-timers` 与最近日志，不能只确认 unit 已安装。

监控自身也要被监控：最后上报时间、抓取失败、告警投递失败、时间同步和磁盘保留。

## 故障排查

1. 从外部症状确定影响范围和开始时间。
2. 对齐发布、配置、DNS、证书和供应商事件时间线。
3. 按入口 → 应用 → 状态服务 → Worker/上游逐层缩小。
4. 使用请求 ID、任务 ID和结构化错误类型关联日志，避免搜索秘密值。
5. 先执行可逆的止损动作：限制入口、暂停领取、隔离账号或回切流量。
6. 恢复后确认指标回到基线并补记时间线与预防项。

## 验证与交付

通过受控方式制造至少一种低风险故障或使用历史数据验证告警表达式，确认告警与恢复通知均可到达。报告覆盖矩阵、阈值依据、告警路由、runbook、静默规则、已验证场景和监控盲区。
