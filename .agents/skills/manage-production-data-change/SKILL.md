# 管理生产数据变更

把数据变更作为独立生产动作。先证明目标集合和兼容性，再允许写入；不要把仓库中的脚本名称或注释当作线上状态真值。

## 建立变更契约

读取应用契约、模型定义、迁移框架、历史脚本、部署流程和备份方式。确认：

- 数据库引擎、版本、主从/集群角色和连接入口；
- 目标表、字段、约束、索引、缓存与派生数据；
- 变更前后不变量及预期影响行数；
- 新旧应用对新旧 schema 的兼容矩阵；
- 是否涉及锁表、长事务、重写大表或队列停顿；
- 恢复方式是反向 SQL、快照恢复、前滚修复还是应用降级。

先识别仓库已有执行器和迁移框架。不要从本地临时拼接未经审阅的生产 SQL，不在命令行历史中展开密码或连接串。

## 准备变更

1. 将查询范围写成只读审计，记录总数、分组计数和代表性样本。
2. 为更新语句增加与审计相同的精确谓词；设置预期最小/最大影响行数。
3. 设计幂等条件，使重复执行保持相同结果，或显式拒绝第二次执行。
4. 对 JSON、金额、额度、状态机、公开名称等字段校验语义，不只校验 SQL 语法。
5. 先在结构相同的隔离副本演练，记录耗时、锁和磁盘增长。
6. 创建一致性备份，并按 `$manage-backup-recovery` 验证其可读性。

敏感业务数据只输出聚合和脱敏样本。生产导出文件使用最小权限并限制为 `0600`。

## 执行

- 在维护窗口内设置合理的 `lock_timeout`、`statement_timeout` 和事务边界。
- 可事务化的小变更使用显式事务，并在提交前检查影响计数。
- 大回填按稳定主键分批，控制批次、间隔、复制延迟和 WAL/日志增长。
- schema 与代码需协同时，优先采用 expand → migrate/backfill → switch → contract。
- 同步更新缓存或运行时注册表时，使用项目已有 reload/restart 入口，避免直接修改内存状态。
- 任何实际影响超出边界、出现锁等待或关键指标恶化时立即停止，不继续“跑完再看”。

Redis 等非关系数据变更必须先确认 key 空间、TTL、序列化版本和持久化模式；SQLite 在线备份使用其原生 backup API，避免直接复制正在写入的数据库文件。

## 验收与回退

重新运行变更前审计，并验证：

- 目标行全部符合新不变量，非目标行未变化；
- 唯一性、外键、金额/额度守恒、状态转换等业务约束成立；
- 应用读写、后台任务和缓存刷新正常；
- 错误率、延迟、锁、连接数和队列积压无异常；
- 重复运行脚本不会扩大影响。

不要默认“回滚镜像”等于“回滚数据”。schema 不兼容时优先前滚修复；只有反向迁移已演练且不会丢失新写入时才执行数据回退。

## 交付

记录脚本版本或校验和、数据库目标、执行人、起止时间、前后计数、备份标识、验证结果、回退决策和遗留风险。禁止在报告中包含密钥、完整连接串或敏感记录。
