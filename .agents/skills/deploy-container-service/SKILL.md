# 部署容器服务

把发布视为“状态迁移 + 流量迁移”，不要只视为重启容器。每次从仓库和线上发现真实值，不把主机、端口、槽位、镜像名、健康路径或超时写死。

## 收集输入

先读取适用的 `AGENTS.md`、Compose、入口脚本、CI workflow、反向代理配置和运行手册，再只读检查线上状态。确认：

- 服务角色及状态所有权：API、调度器、Worker、数据库、队列、网关；
- 当前与目标不可变镜像标识，优先完整 Git SHA 或 digest；
- 活跃槽、备用槽、流量入口、健康与就绪检查；
- 数据库迁移方向及新旧程序与 schema 的兼容矩阵；
- 长任务、定时任务、结算等单活职责及排空语义；
- 已验证的回滚镜像、配置和数据恢复点；
- 允许中断时长、变更窗口、验收责任人。

已有发布脚本时优先调用并审阅脚本，不另写一套并行流程。不要用浮动 `latest`，不要把“容器运行中”当作“服务可用”。

## 设计发布序列

按依赖顺序组织变更：

1. 执行预检：磁盘、内存、端口、镜像可拉取、配置可渲染、依赖可达、备份可用。
2. 记录当前运行真值和回滚目标，不把未验证的当前版本登记为回滚点。
3. 先启动不接生产流量的候选实例，校验版本、角色、依赖和 readiness。
4. 若有数据库变更，按 `$manage-production-data-change` 的兼容窗口执行。
5. 对长任务服务先停止领取新任务，再等待在途任务排空；超时后停止并调查，不强杀后宣称成功。
6. 原子切换代理配置或服务发现，先校验配置再 reload。
7. 从外部入口验收，再处理旧实例；保留明确的观察期和回滚窗口。

单活职责必须有唯一真值来源。蓝绿 API 可以短暂并存，但调度器、队列消费者、Cookie 保活、结算器等不得因双槽同时运行而重复执行。非幂等请求不得在已发送后由代理自动重试。

## 选择恢复策略

- **代码或配置失败且 schema 向后兼容**：切回已验证旧镜像。
- **schema 已前滚且旧程序不兼容**：不要盲目回滚二进制；使用兼容新 schema 的新程序恢复服务，或执行已演练的数据回退。
- **Worker 替换失败但任务真值仍完好**：恢复可消费该 schema 的 Worker，调用项目已有 resume/reconcile 能力。
- **首次部署失败且无验证版本**：停止不健康入口，不伪造自动回滚成功。
- **代理切换失败**：恢复已备份配置并再次校验、reload。

回滚也是一次发布，必须互斥、验证并记录。

## 验证

至少验证：

- 镜像版本、环境、角色、槽位与预期一致；
- readiness、外部 HTTPS、核心读路径和一条受控写路径通过；
- 旧实例不再接新请求，长任务无丢失或重复；
- 数据库连接数、队列积压、5xx、延迟和资源指标无异常；
- 代理实际 upstream 与记录的活跃槽一致；
- 回滚命令及目标仍可用。

真实生成、支付或其他有成本/副作用的验收必须使用授权测试账户和明确限额。

## 交付

报告变更前后版本、流量切换点、迁移结果、验收证据、观察窗口、回滚边界和未验证项。不得仅凭命令退出码声明发布成功。
